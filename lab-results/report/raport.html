Authentic Rapid Reset (PoC bot)

In addition to the h2load flood, the real CVE-2023-44487 pattern was executed: a custom bot opens an HTTP/2 connection, sends HEADERS and immediately RST_STREAM (stream cancellation) in a loop. This exposes the attacker-victim asymmetry — and demonstrates the nginx patch in action.

Conclusion: on a patched nginx (>=1.25.3) pure Rapid Reset does not bring the server down — the reset-counting mechanism terminates aggressive connections. The cost on the client side (half a million frames) is enormous relative to the gain (zero). The attack signature, however, is perfectly visible: extreme ratio of streams to maintained connections.

nginx is resilient to Rapid Reset. Even unpatched 1.25.1 is not saturated by the fleet — cancelled streams are cheap to handle, and the keepalive_requests limit closes abused connections. This is why "unpatched vs patched" produces a similar, moderate effect (unlike application servers that collapsed under CVE-2023-44487).
Load grows with botnet size. The trend is upward (on 4 cores it's noisy due to CPU contention). Per-IP hardening limits a single bot, but a botnet distributes traffic across many IPs — so the aggregate still grows with the number of bots. This is a key lesson about distributed attacks.
C2-controlled operation. The fleet consists of Sliver implants (mTLS); the operator triggers Rapid Reset on all bots at once with a single execute command. Procedure and script: lab-results/README.md.

Conclusions

Without defense, load scales with intensity. Victim CPU grows linearly with the number of attacking clients: 11% -> 26% -> 42% -> 50% -> 64%, and concurrent connections 5 -> 51. With an efficient static server the flood doesn't reach 100% (nginx is fast), but the cost is real and growing.
Hardening flattens cost to idle level. Per-IP rate-limiting (limit_req 20 r/s, limit_conn 20) keeps CPU at ~2% at every intensity level. The flood is rejected with a cheap 429 at the edge instead of loading the backend — at the 80% threshold that's 4,951 rejections vs 49 served.
The protocol patch already works. Authentic Rapid Reset (562k RST_STREAM) does not overload the server — nginx terminates aggressive connections (29 reconnects, max 2 connections, 0 successful responses). Defense in depth (rate-limit) adds to the built-in patch.
Detection is feasible and cheap. The signature is clear in the metrics: spike in active connections and requests/s, extreme ratio of streams to connections, CPU increase with negligible complete 2xx responses. The same metrics are collected by Zabbix in real time (section below).

Methodology and proof of work

Test setup

  • Victim: nginx 1.27.5 with HTTP/2 (self-signed TLS), container with 1 CPU core limit, labnet network (internal, no internet).
  • Flood attack: h2load -c <clients> -m 64 — intensity calibrated by number of clients to target victim CPU.
  • Protocol attack: custom PoC rapidreset (Go) — HEADERS + immediate RST_STREAM in a loop, with reconnect.
  • Defense: configuration swap to nginx.hardened.conf — http2_max_concurrent_streams 32, keepalive_requests 100, limit_req 20 r/s (burst 40), limit_conn 20, rejections -> 429.

Measurement

  • Victim CPU from cgroup v2 (cpu.stat usage_usec, delta/second) — 1 s resolution.
  • Connections and requests from nginx stub_status; status distribution from h2load client report.
  • Threshold calibration (measured CPU for increasing client counts): c=4->9%, c=10->18%, c=25->40%, c=35->56%, c=50->82%.

Key commands

docker compose up -d --build                 # victim + loadgen + bot (+ Zabbix)
docker compose exec bot rapidreset -url https://victim:443 \
     -requests 20000 -concurrency 1000        # authentic Rapid Reset
docker compose exec loadgen h2load -c 50 -m 64 -D 30 https://victim/   # flood ~80% CPU
docker compose -f docker-compose.yml -f docker-compose.override.yml \
     -f docker-compose.monitoring.yml -f docker-compose.hardening.yml up -d victim  # hardened mode

Raw data (1 s time series and per-scenario summaries) collected to CSV files: results.csv (163 samples), stats.csv (status distribution). Experiment: 5 thresholds × {vulnerable, hardened} + baseline + bot, each scenario 30 s.
